# Database enforcement and privilege gate

Design only. This document specifies future reviewed SQL behavior; it contains no executable migration. Schema remains unchanged.

## Role separation

| Role | Allowed | Forbidden / boundary |
| --- | --- | --- |
| platform database administrator | Provision isolated roles, backup/restore, emergency controlled ownership repair | Never a Function credential; manual break-glass approvals, audit and rotation required |
| hv_schema_owner (NOLOGIN) | Own schema, tables, policies and constraints | No runtime membership; no ordinary application access |
| hv_migrator (controlled login) | SET ROLE to schema owner in migration pipeline; approved DDL and backfill | Not exposed to Functions/frontend; no routine business access; revoke role after job |
| hv_operation_owner (NOLOGIN) | Own narrowly defined SECURITY DEFINER operations; exact table DML under FORCE RLS policies | No superuser/BYPASSRLS, CREATE/GRANT, or membership in schema owner; audit UPDATE/DELETE/TRUNCATE denied |
| hv_runtime (login) | CONNECT, application schema USAGE, EXECUTE on enumerated operations | No direct tenant table DML/SELECT, role switching, object ownership, CREATE, TRUNCATE, REFERENCES grants, trigger disabling, or arbitrary function creation |
| hv_audit_reader (optional controlled role) | Execute scoped audit read operation only | No broad audit table read, export or mutation; audit.read checked per call |

Revoke default PUBLIC function EXECUTE and schema CREATE, review inherited/default privileges, restrict schema search paths and qualify all object names. SECURITY DEFINER routines use fixed `pg_catalog` plus a trusted non-writable application schema, validate every argument and perform no interpolated dynamic SQL. Do not grant general-purpose arbitrary query routines. Function owners need explicit policies and least table privileges; FORCE RLS applies to ordinary owners but superusers/BYPASSRLS still bypass it. Migration/admin identities are necessarily privileged and cannot be made unable to tamper; mitigate with isolation, approval and external audit/backup controls.

Platform must support separate role credentials, custom LOGIN/NOLOGIN roles and grants, object ownership, forced RLS, constraint triggers, trusted function deployment, transaction-local settings and reliable pooled connection pinning. Confirm that platform migrations can act as schema owner without supplying that identity to Functions. If a platform-provided runtime connection is privileged, merely issuing SET ROLE is insufficient because RESET ROLE could restore privileges: require a true restricted login. If this cannot be supplied by Netlify's managed connection configuration, implementation is blocked.

## Isolation decision: restricted operations plus FORCE RLS

Runtime may invoke only reviewed operations. Each operation checks current active membership and explicit permission before accessing tenant resources. Tenant tables also use FORCE RLS with read USING and write WITH CHECK; absent/malformed context denies access. Global users/sessions are accessible only through identity-specific restricted routines, not tenant-wide grants. Organization bootstrap is a dedicated operation with a newly generated organization ID, server actor context, no membership prerequisite, and no arbitrary access to existing organizations.

Transaction-local actor, organization, request correlation and verified session are installed by server code on an acquired connection after session validation. Use parameterized `set_config(..., true)` after BEGIN; never session SET, URL roles, browser permission claims or global mutable context. Browser organization selection is an untrusted selector, not authority. RLS predicates require both organization equality and active actor membership, with operation-specific permission/scope enforced by routines. Bootstrap and owner-integrity checking need narrowly scoped special policies so that inactive memberships cannot hide rows from constraint validation; no context-only universal bypass.

Custom PostgreSQL settings are **not unforgeable capabilities**: any caller with SQL execution can set them. Runtime restrictions reduce blast radius but the trusted Function server remains the authority asserting actor identity. No public SQL endpoint or generic operation is allowed. Stronger resistance to runtime compromise would require signed assertions independently verified in the database; not selected or claimed here. Internal definer code must not broaden context beyond its validated operation. Same-tenant authorization remains distinct from RLS row visibility.

Acquire → BEGIN at chosen isolation → validate session/global revocation → organization lock → active membership/permission checks → install scoped context → operation/audit/idempotency → COMMIT → release. Identity/session verification happens both before transaction entry and under the applicable session row lock for critical operations. Context used for membership lookup must be handled through restricted routines rather than direct runtime SELECT. No await of external APIs inside the database transaction. All calls use the same acquired client; no pool.query, HTTP convenience SQL or separate top-level Drizzle instance inside it. On any exception ROLLBACK; if rollback fails or connection state is uncertain discard client. Verify pg_backend_pid identity through the entire transaction in isolation. Do not assume session-pool semantics beyond the transaction. Handle cancellation, timeouts, reconnects, warm Function reuse and credential rotation explicitly.

## Ownership and provisioning

Enforce unique (organization_id,user_id), valid role enumeration, positive versions and well-formed allowlisted delegated permissions; deny management delegations for employee/contractor. Owner pointer must reference a real global user. Future composite FK (organization_id,owner_user_id) → membership (organization_id,user_id), DEFERRABLE INITIALLY DEFERRED, ensures accountable membership exists at commit. A partial unique active OWNER index establishes at most one; deferred constraint triggers on organization insert/owner update and membership insert/update/delete establish at least one, matching pointer and active role. Trigger validates old AND new tenant IDs on any attempted reassignment and reads all membership rows through a dedicated integrity role/policy. Tenant key updates are prohibited through runtime routines. Triggers alone without proper locks do not solve concurrency.

Every ownership/membership-changing operation takes the organization row FOR UPDATE first, then membership rows in deterministic ID order. Trigger path also locks the organization for privileged maintenance changes; ordinary runtime cannot bypass routines. Provisioning uses SERIALIZABLE, inserts organization, active owner, default-off policy, audit and durable idempotency outcome in one transaction. Deferred references allow temporary cyclic absence until commit. Transfer demotes the old owner before promoting the new owner to satisfy the immediate partial unique index, updates pointer and version, and commits only if deferred checks succeed. Last owner revocation/deactivation/deletion fails unless ownership transfers atomically. Global user deletion cannot cascade through accountable organizations. Organization deletion is a separately authorized lifecycle/retention operation, unavailable to runtime here.

Provisioning idempotency cannot depend on the not-yet-created organization's FK. Design a separate global bootstrap idempotency scope keyed by verified actor + operation + key; reserve it before organization creation, and store the resulting organization ID in the same transaction. Current schema has only tenant idempotency and needs an authorized later change.

## Revocation and authorization races

All permission-sensitive operations acquire the organization lock before membership authorization and hold it through commit. Revocation takes the same lock, deactivates membership, increments membership/version authorization epoch and appends audit. A mutation that acquired the lock and commits before revocation is valid; an operation serialized after revocation commit is denied. Revocation is immediate for new operations after commit, not retroactive cancellation of already committed work. SERIALIZABLE transactions which began earlier must retry on serialization failure and recheck authority. Tenant reads with sensitive output use the same reauthorization ordering where strong revocation is required; already sent responses cannot be recalled. Global session revocation takes session/user-epoch locks in the agreed order: user/session → organization → membership → resource. This avoids acquiring them in reverse order in tenant operations. No durable authorization cache substitutes for these checks.

## Audit and idempotency

Business operations append a server-attributed audit event in the same transaction. Audit table permits INSERT only to operation owner; runtime has no direct INSERT to forge actors. UPDATE, DELETE and TRUNCATE fail through grants and defensive mutation triggers. No ON DELETE CASCADE from organization/user; archive references retain attribution without requiring undeletable PII. Failed transactions cannot retain their transactional audit event: denied-attempt security events need a separate minimal append path after rollback, without leaking tenant existence. Privileged DBA tampering cannot be excluded; external tamper-evident archival is a later hardening requirement.

Tenant idempotency unique scope is actor + organization + operation + key. Canonical payload hash includes operation/schema version; mismatched reuse fails, never executes. Reserve key via unique conflict handling, lock winning record, verify current authority even on replay, and return stored outcome only to an authorized same-scope caller. Mutation/audit/result commit together. Concurrent calls converge; rollback removes incomplete reservation; process crash after commit retries to the recorded result. Uncertain COMMIT must query the same key after reconnection before any rerun. Do not catch a unique violation and continue an aborted transaction without savepoint or ON CONFLICT. Define result status, response version and bounded payloads; no credentials/tokens in results. Proposed retention minimum is 30 days; logical operation uniqueness must outlive retry keys for non-repeatable actions. Expiry/cleanup cannot make an already billed entry billable again. Retention policy needs approval before implementation.
