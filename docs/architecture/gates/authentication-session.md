# Provider-neutral authentication and session design

No authentication integration, schema mutation, login UI, provider calls or protected endpoints is implemented.

## Boundary contracts to add only in an authorized sprint

A provider verifier accepts an untrusted request credential and returns a verified identity proof containing issuer, subject, assurance/auth_time, expiration and verification provenance. A session authority validates an opaque application cookie, checks server-side state and returns a server-created principal with global user/session IDs. A membership authorizer accepts this principal and an untrusted organization selector, and reads current active membership/permissions within the operation transaction. Principal creation is inaccessible to presentation. Existing AuthorizedContext is structurally forgeable and `AuthorizationPort.require(userId,...)` accepts an arbitrary ID; future contracts must bind userId to a validated principal and transaction handle, not accept browser userId. `TransactionPort.serializable` must hand the callback a scoped transaction capability to prevent ambient connection escape.

Global identity mapping needs unique (issuer,subject), not the current subject-only uniqueness. Email is mutable, not an identity key or authority. Account linking requires fresh proof of both identities; never link automatically by matching email. Verified email, MFA and assurance are policy inputs, not organization roles. Creating a global user must not auto-create a personal workspace or tenant; organization creation is an explicit separately authorized action.

## Provider verification

For JWT providers: cryptographically verify signature against configured HTTPS issuer keys; allowlist algorithm/issuer/audience; enforce exp, nbf, issued-at, nonce and token purpose, reject unsigned tokens and issuer/audience confusion. Validate key selection without trusting arbitrary token URLs; bounded JWKS refresh on unknown key, fail closed if unable to verify. Valid signature is not evidence of non-revoked provider session. Use documented introspection/session APIs or signed lifecycle events plus application revocation; explicitly define any provider-global revocation lag. Callback flows require PKCE, state, nonce, exact redirect allowlist and replay controls. Do not decode and trust token roles or user metadata. Webhooks require signature/time/replay validation.

Netlify Identity is a candidate implementation through @netlify/identity only. Its package and server validation/revocation APIs are not installed or tested here. SDK hydration/user convenience results must not be equated with server validation without evidence. No enablement or provider selection occurs. Netlify team SSO context represents platform team users, not workforce SaaS identities. An external provider must also remain behind this contract and require a separate platform decision.

## Application session model

Propose a cryptographically random opaque cookie token, storing only its cryptographic hash in PostgreSQL with user ID, created/last-seen timestamps, idle/absolute expiration, auth_time/assurance, revoked_at, version and global session epoch. Provider refresh/access credentials, if needed, remain encrypted server-side with managed-key access separated from runtime data; never in audit, idempotency, browser storage or logs. Current schema has no session/identity-binding tables and is not modified.

Cookie: Secure, HttpOnly, SameSite=Lax, Path=/, host-only __Host- prefix. POST/logout/mutations require CSRF token and strict Origin validation; no wildcard credential CORS. Rotate after login, refresh, privilege elevation and account recovery; revoke prior tokens or allow only a narrowly specified in-flight refresh window. Proposed limits: 30-minute idle expiry, 12-hour absolute expiry, maximum five-minute assurance age for owner transfer/security changes. Limits are design defaults requiring approval, not active behavior. Refresh is one-time rotation with atomic replay detection and family revocation. Concurrent legitimate refresh uses explicit serialized handling; never extends an expired/revoked family. No persistent login option in initial implementation.

Validate cookie hash/state, expiry, user disablement and global session epoch on every protected request; then reauthorize organization membership for every operation. No browser role/org claims or provider metadata grant authority. Missing proof, dependency failure or lookup timeout denies access. Generic 401 for no valid session; authenticated missing tenant/resource returns non-enumerating denial. Responses are private/no-store, with no tenant data cached by CDN; rate limiting and security event logging need separate approved implementations.

## Revocation and transaction semantics

Membership revocation affects only that organization, leaving unrelated organization memberships intact. Role/grant changes increment membership version and invalidate all cached tenant capabilities. Logout revokes one application session; logout-all, user disablement, recovery and confirmed provider compromise increment a global epoch/revoke session families. Provider deletion disables mapping and sessions; lack of provider events cannot be described as immediate global revocation. Recheck session/global epoch and current membership under locks for critical mutations in the same transaction; use the global→organization→membership→resource order. Revocation committed first blocks later authorized work; already committed actions are not undone. Return idempotency results only after fresh reauthorization.

Monitoring offline leases are separate short-lived signed capabilities with device/user/organization, policy version and expiry. Membership/session revocation stops new leases immediately after commit; already offline devices may continue only until lease expiry. Default expiry is zero. Transparent stop/disconnect remains available; do not promise remote instantaneous revocation while offline.
