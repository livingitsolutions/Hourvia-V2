# Migration generation, reconciliation and recovery gate

No migration file, configuration, snapshot, deployment or database connection is created in Sprint 0.1.

1. Inventory exact PostgreSQL version/extensions, managed role capabilities, connection routes, branch isolation and backup/PITR availability in a separately authorized isolated environment. Confirm automatic schema generation and deployment application behavior; do not infer it from SDK source. Platform previews may copy production data, so they are not approved integration-test targets.
2. Pin reviewed stable Drizzle/Kit versions. Compile schema in a disposable artifact workspace and generate outside any deploy-consumed directory only after explicit authorization. Preserve provenance: schema hash, lockfile hash, generator version, SQL hash, previous snapshot/journal state. If platform automatically emits migrations before review, halt deployment and gate activation; do not let generation imply application approval.
3. Review SQL and metadata together. ORM-generated DDL does not implement every owner constraint, custom role, trigger, forced RLS policy or function. Track custom SQL with a canonical reviewed security manifest and catalog expectations so later generation cannot silently remove them. No ad hoc remote DDL. Provisioning roles may require platform-admin setup outside normal schema migrations; record exact applied state and approvals.
4. Reconcile schema, ordered migration journal, immutable snapshot lineage and actual isolated catalog. For this fresh design there is no baseline migration or snapshot. Confirm a genuine empty target in isolation before generating the first baseline; never stamp a nonempty database as current without reconciliation. Introspected objects unsupported by Drizzle must remain in the security manifest. Fail on unexplained drift or missing applied files. No production introspection is authorized here.
5. Apply candidates to disposable PostgreSQL using a matching restricted migrator, then run the integration matrix as runtime. Verify upgrade from each supported prior release, cold bootstrap, constraints at COMMIT, function privileges, and previous/current app compatibility. Capture evidence and approved checksums.
6. Use expand-contract releases: additive schema first, compatible code second, backfill in bounded reviewed jobs, destructive cleanup only after old Functions and retries expire. Set lock/statement timeouts, estimate table locks and data rewrite costs, and use transactional DDL where supported. Operations needing nontransactional DDL, such as concurrent indexes, require documented platform support and a separate recoverable phase. Do not assume deploy migration runner wraps all files in one transaction.
7. Only after approval put reviewed SQL in netlify/database/migrations. Netlify deployment applies those migrations before publishing, including previews. Verify deploy serialization/ledger locking, checksums, failure behavior and repeat application semantics. Pipeline must fail closed on unreviewed generation, changed checksums, unexpected pending migrations or security-manifest drift. Migration role credentials never enter runtime bundles.
8. Snapshot reset/regeneration is permitted only for proven never-applied local artifacts in an authorized later task; retain applied snapshots/files forever and roll forward. Never rewrite migration history after local, preview or production application. Database-state commands are not run in this gate.

## Recovery

Before any implementation release establish approved backup frequency, demonstrated isolated restore, encryption/access controls and explicit RPO/RTO targets. Current platform context proves none of these; they are P0 release gates. Migration failure halts publication; roll back the open transaction where possible, reconcile partial/nontransactional work and prepare a new forward repair. Do not blindly replay ambiguous migrations. Code rollback is allowed only when the previous application remains schema-compatible; never assume reverting deploy reverts schema.

For corruption or severe failure: stop writes, preserve audit/evidence, use a separately authorized restore to a fresh isolated branch/database, verify catalog/security/idempotency/allocation consistency, reconcile lost writes and external effects, then obtain approval for controlled cutover. Never restore production in place without incident approval. Restoration may resurrect revoked sessions or memberships; revoke session families and revalidate authorization state against incident records before reopening access. Exactly-once billing and audit lineage require reconciliation, not simply a restored backup. No restore, deploy or destructive rollback occurs in this gate.
